# Documentación: Guía para la Creación y Gestión de Spikes

Esta guía tiene como objetivo estandarizar el uso de **Spikes** dentro del equipo de desarrollo. Se define su propósito, cuándo deben utilizarse, cómo deben documentarse y se proporcionan herramientas prácticas para su correcta implementación.

Durante la revisión de procesos anteriores, se identificó la necesidad de mejorar la claridad en las tareas de investigación técnica. Esta guía surge para garantizar que los Spikes se ejecuten con un enfoque claro, entregables definidos y en un tiempo controlado.

---

## ¿Qué es un Spike?

Un **Spike** es una tarea de investigación técnica utilizada para resolver dudas, explorar tecnologías o tomar decisiones técnicas fundamentadas. No genera entregables funcionales, sino **conocimiento validado**.

### ¿Cuándo utilizar un Spike?

- Existen dudas técnicas o incertidumbre en la solución.  
- Se requiere investigar una herramienta, API o librería.  
- Es necesario tomar decisiones arquitectónicas informadas.  
- Se quiere evitar avanzar con supuestos o riesgos técnicos.

---

## ❌ ¿Qué NO es un Spike?

- No es una tarea de desarrollo o funcionalidad.  
- No se entrega código final al cliente.  
- No reemplaza una User Story.  
- No es una excusa para posponer decisiones.

---

## Diferencias entre Spike y User Story

| Spike | User Story |
|-------|------------|
| Explora o investiga una solución | Implementa una funcionalidad |
| No genera código final | Genera un entregable funcional |
| Tiene un objetivo técnico | Tiene un objetivo de usuario |
| Tiene un timebox (límite de tiempo) | Puede extenderse según su alcance |

## ✅ Buenas Prácticas para Spikes

- Definir un **problema técnico claro**.
- Establecer un **objetivo concreto**.
- Fijar un **timebox limitado** (máx. 1 sprint).
- Definir **entregables revisables**: doc, prueba, matriz de decisión, etc.
- **Documentar los hallazgos** y compartirlos con el equipo.
